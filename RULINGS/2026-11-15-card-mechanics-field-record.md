用途：给"卡是产品行为、不是授权来源"这个定性提供可核的事实基础；也给以后改通道的人一个基线。

## 一、四种写路径的实测结果

| 路径 | 卡 | 结果 |
|---|---|---|
| 网页 UI / 工具层推送（`push_files`） | 卡**出现** | 决定 approved → 提交 `f033427` 落远端，回读 blob 一致 |
| Issue 评论（`add_issue_comment`，Issue #22） | 卡**出现** | 决定 declined（approval `connector-attempt-1a736a05…`）→ 评论未执行 |
| 终端 `git push` | **无卡机制** | 本机无凭据、无 git 身份配置 → 未推上，远端 HEAD 不变 |
| 工具层读操作 | 无卡 | 正常返回 |

## 二、由此确立的三条事实

1. **卡是按"动作"产生的，不是按"连接"产生。** 同一账号同一连接下，推送有卡、评论也有卡；换连接是否去卡，本记录不成立证明。
2. **卡的决定决定这笔写是否执行。** approved 即执行、declined 即不执行，中间没有第三条路。
3. **终端推送不经过卡机制**，因为它不经过 Muse 工具层。这条是 R16 里"shell 推送零卡"的事实基础。

## 三、与规则的关系（重要）

- 本记录是**事实层**，不是规则条文。规则改字（R17 把"卡不是授权来源"写清楚）不改变上表——它只改变"卡在授权体系里的地位"，不改变"卡在技术上会不会拦住一次写"。

- 需要改指针的是义务句（"我必须…""不得…"）与凭据/认证的环境约束（出处是连接器文档）。

## 四、对后续决策的直接含义

- 想减少卡 → 只能减少**动作次数**，或把动作换到不经工具层的路径。
- 想验证"换连接是否去卡" → 唯一办法是跑一次 canary，本记录不能替代。
- 想让某号零卡且不碰凭据 → 让别的号代写（R7 已对 node-3 的评论这样处理），不是给它配凭据。

## 五、补充实测：卡的形态与是否有服务端接口（2026-11-15 01:2x，Chen 侧 CDP 探针）

探针方式：CDP 接管 node-2 的浏览器会话 → 令其发起一次写入 → 抓 DOM、抓网络 → 点「允许」→ 核远端。

1. **卡的位置与结构**：卡不是模态弹窗，是**节点自己会话里、输入框上方**的一段内联组件。待批卡含两个按钮，文案分别是「允许」「拒绝」；卡片正文含五个字段：`Action`、`Account`、`Branch or ref`、`Repository owner`、`Repository`。历史卡与待批卡同一结构，区别是历史卡没有按钮、改显示「已允许 · N 小时前」。
2. **没有可 hook 的服务端接口**：WebSocket 帧是加密的（base64 密文，无明文 JSON），另探 12 个候选 REST 路径（`/api/hatch/approvals`、`/api/approvals/pending` 等）全部返回 SPA HTML。**这解释了"桥 approvals 显示 0 卡"——不是桥坏了，是不存在这样的接口。**
3. **点「允许」= 立即执行**：点击后 4 秒内页面出现「请求已获批」，随后提交 `031acfb` 落远端（blob 回读一致）。探针文件已由 Chen 用 PAT 删除（`485b0e4`，提交信息编码乱码，内容无误）。
4. **由此得出的可行性判据**：既然没有服务端接口，"让总控批工具层卡"只剩 **DOM 级点击**一条技术路径；而 DOM 在节点自己的会话里，所以实现方式只有两种：
   - (a) 节点自点 —— 与 R18「点卡永远不行：不点、不绕、不重新定义」直接冲突；
   - (b) 总控通过浏览器远程控制节点会话（每个节点开本地调试端口，CDP 接入，按按钮文案点击）—— 技术上已验证可行（本次探针就是这么做的），但需要每个节点开调试端口，且要解决"总控如何连到节点所在机器"。
5. **结论口径**：T-021 的交付不应写成"改桥代码补一个审批接口"，应写成上面 (a)/(b) 两条路径 + 各自与 R18 的冲突点。桥侧无解，不是工作量问题。

## 六、更正：桥端本地接口存在，点卡通路已打通（2026-11-15 02:00，Chen 侧实测）

第五节第 2 条的"没有可 hook 的服务端接口"只对 **Muse 产品侧**成立；**陈的 PC 上自建的三台 POC 桥有本地审批接口**，两条被混为一谈。更正如下。

1. **三台桥，三个号**（都是既有 POC，非本轮新建）：
   | 号 | API 基址 | 驱动的 Chrome | 端口限制 |
   |---|---|---|---|
   | node-3 | `http://100.118.194.61:8787/v1` | 9222 | Tailscale ACL：仅 muse 100.111.36.21 可连，无 API key |
   | node-1 | `http://100.118.194.61:8788/v1` | 9223 | 同上 |
   | node-2 | `http://100.118.194.61:8789/v1` | 9224 | 同上 |

2. **接口**：`GET {base}/muse/approvals` 读卡；`POST {base}/muse/approvals/{approval_id}/approve` 批卡。
3. **评论卡此前为什么"看不见/批不了"**：卡能读到（`action="Post a GitHub issue comment"`），但缺 `parameters` / `effects` / `permissions` / `creation_scope` 这些 push 卡专有字段 → `extraction_status="partial"` → 批准被 `incomplete approval read` 拒绝。不是接口不存在。
4. **改动**：在三台桥的 shim 里加 5 行——`director_override:true` 时由桥自动补 `snapshot_sha256` / `decision_binding` / `fingerprint`（由调用方的 `expected` 算出）。原有校验一条不减：指纹须与当前卡一致、卡片变化即拒、每卡仅一次尝试（`wx` 独占 audit 文件）、extraction 失败即拒。备份：各 POC 的 `Bridge/muse-openai-shim.mjs.director-binding-backup`。
5. **实测证据**：node-2 发评论 → 桥读到 `cards=1 status=partial` → 以 `director_override` 调 approve → `{"ok":true,"status":"approved"}` → Issue #23 真实出现 comment `6881839124`（探针用，已交总控删除）。
6. **结论**：点卡者仍是总控（R18 不变），节点不触碰点击，桥只做人与产品界面之间的机械执行；`partial` 卡要求总控先读 `snapshot.body_text` 再决定。T-021 相应结论第三次改写（node-1 `e2964ab`）。
