# T-074 首轮快照导出 30 秒超时排查（恢复 <120 秒的卡点）

- Issue: #69
- 执行方：Codex（总控 VM 本地）
- 来源：T-073 实测遗留问题（Chen 直令 2026-11-19 20:09 的 <120 秒目标未达，卡点在此）
- 边界：不改 RULES；只动恢复/导出脚本（deploy/ 下的 repair-after-vm-replacement.sh、snapshot-export.sh），不动 Tower 业务代码；若根因在后端代码，只写进报告，不许擅自改后端。

## 问题

T-073 两轮完整恢复测试总耗时 235.82 秒 / 248.99 秒，均未达 <120 秒目标。分段显示服务本身 1.85–4.96 秒就拉起来了，耗时全在 snapshot timer 自检等待：首轮导出两次都在后端接口 30 秒超时失败（日志：2026-11-19T12:17:15Z 与 12:21:43Z `snapshot export FAILED: TimeoutError: timed out`），随后新快照推进，自检第二轮才通过。两次失败都发生在服务重启后约 90–100 秒（重启时间 20:15:40 与 20:20:05，失败 20:17:15 与 20:21:43），重启之间的导出（20:19:27）是成功的。

## 任务

1. **定位根因**：首轮导出为什么超时。是后端 overview 接口冷启动慢（git 读取、对账计算、冷缓存），还是导出脚本自身的超时太紧，还是 git fetch/push 慢。用实测分清：重启后立即手动调一次 overview（计时）、看后端日志、看导出脚本的超时设置与哪一步超时。
2. **修**：按根因修，首选不改业务代码的办法，例如修复脚本在启用 timer 前先暖一次后端（调一次 /api/v1/overview，等它返回再起 timer），或放宽首轮导出的超时，或让 timer 自检不把撞上重启窗口的首轮失败计入。修完不许削弱自检（timer 必须真实触发、快照必须真实前进）。
3. **验**：复用 T-073 的办法——停掉两服务 + timer，跑修复脚本并计时。目标：timer 自检首轮通过，总耗时向 <120 秒靠拢；贴实测数字与分段。若修完仍达不到，贴分段数据并单独报，不许为达标改自检。

## 验收

- 根因（带证据：哪一步、多少秒、日志行）；
- 改动位置（文件 + 行号）；
- 实测恢复总耗时与分段，是否首轮通过；
- 若需改后端代码，写进报告当发现，不提交后端改动。
