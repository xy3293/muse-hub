## 探测清单（9 项，逐项给结论 + 证据）

1. **`muse.db` 的路径、schema、只读访问方式和 patrol 可见性**：`patrol.sh` 所在执行环境能否只读打开 DB？以什么用户、什么路径、什么命令打开？只读打开是否成功？
2. **run 行与 task／attempt／wake 事件的可靠关联字段**：`runtime.execute_resolve_runs` 里哪些字段能可靠关联到具体任务和 attempt？给出真实字段名与示例值（脱敏）；没有可靠字段就写“无”，不得猜一个字段名。
3. **DB 的 WAL／锁／写入延迟**：只读查询是否会干扰运行时？WAL 模式、锁机制、记录写入延迟如何？只读查询，不得写运行时数据库，不得修改内部表。
4. **共享状态目录在 patrol 侧的读写权限**：`/home/hatch/hooks/state/` 在 patrol 执行环境中是否可读可写？（T-008 已验证 worker 侧，本项补 patrol 侧。）
5. **worker 环境变量缺失确认**：确认 worker 内没有 `HATCH_HOOK_STATE_DIR`、`HATCH_HOOK_ID`；结论是原始路径 `/home/hatch/hooks/state/` 作为显式配置。
6. **独立 heartbeat 的父进程识别和孤儿退出探测**：后台 heartbeat helper 如何识别父进程（PID＋启动标识，防 PID 复用）？父进程消失后 helper 是否自行退出？实测一次（小规模即可），不得仅按 PID 杀进程。
7. **现有 GitHub 访问方式、缓存、ETag 能力和现有凭据可见性**：巡逻现在怎么读 GitHub？有无本地缓存？接口是否支持 ETag／条件请求？节点有无可复用的已授权认证凭据（只写“有／无、存放位置类型”，**不得输出凭据值**，不得贴 token）。
8. **当前 patrol 与 Hook 基线确认**：`patrol.sh` 版本、Hook timeout（600 秒）、300 秒巡逻周期、`flock` 状态，逐项核对现状。
9. **能力矩阵**：9 项汇总成一张表（已验证／部分验证／不支持／未知），未知项不得在设计中按“已支持”处理。
