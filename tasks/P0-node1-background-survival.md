# P0：node-1 后台进程 600 秒存活验证（单节点最小实验）

## 背景
Worker（Muse 唤醒）有 600 秒硬上限，到点被杀。问题是：它启动的后台进程会不会跟着死？这决定长任务能不能走“节点后台进程”路线，还是只能走“巡逻驱动恢复”。先验平台边界，再决定建什么。

## 目标（只做这一件事）
验证 node-1 启动的后台 Python 进程能否活过 600 秒 Agent 终止。

## 方法（两阶段，同一任务）
### 阶段一：启动（第一次唤醒）
1. 先检查是否已有 P0 测试在跑：查看工作区是否存在 `p0-heartbeat.txt` 与 `p0-job.json`。如已存在，**不要**重新启动，直接跳到阶段二。
2. 如不存在，写一个 Python 测试程序：循环 900 次，每秒向 `p0-heartbeat.txt` 追加一行“序号 + 时间戳”（共 15 分钟，无副作用，只写本节点工作区）。
3. 以独立后台进程方式启动它（nohup / setsid 任选其一，记录你用的方式），把 PID、进程启动时间、job_id 写入 `p0-job.json`。
4. 不要等待程序完成，结束本次执行。

### 阶段二：检查与收集（后续巡逻唤醒）
1. 每次被唤醒，先读 `p0-job.json`，检查该 PID 的进程是否仍存在，`p0-heartbeat.txt` 是否仍在增长（行数与最后时间戳）。
2. 若 15 分钟未到且进程仍在跑，只记录状态，不重启、不干预，结束本次执行。
3. 若进程已结束或 15 分钟已过，收集结果：进程是否存活过 600 秒、心跳共多少行、最后时间戳、退出码（如能取到）。把结果写入 `results/node-1/p0-background-survival.md` 并推送，在本 Issue 下回复结论。

## 验收标准（全部必须通过才算 PASS）
1. Agent 被 600 秒终止后，后台 Python 进程仍存活。
2. 心跳文件在 Agent 被杀后仍持续增长。
3. 后续唤醒的 Agent 能凭 `p0-job.json` 找到原任务，不需总控重新派工。
4. 若以上任一失败，如实报告失败，并判断可能原因（进程组、cgroup、容器还是整个运行环境被清理），不要只写“nohup 不工作”。

## 特别说明
- 若你完全无法执行 shell 命令（不能启动 Python 进程），直接报告这一点——这本身就是答案（节点不能跑代码），同样记为有效结论，不要强行绕过。
- 只写本节点工作区与 `results/node-1/`，无其他副作用，不碰密钥，不做不可逆操作。
