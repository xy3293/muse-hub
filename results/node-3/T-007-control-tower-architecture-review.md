## 结论先行

**总体结论：架构方向可行，无需重新设计。** 只读 GitHub、私有访问、SQLite 只存自有数据、不引入不必要中间件，这四条主干判断正确。10 项审查中：**高风险 0 项，中风险 6 项，低风险 4 项**。

**最优先处理的三件事（冻结数据模型与 OpenAPI 之前必须定）：**

1. **数据源与限额方案未定（第 8 项，中）**：未认证 GitHub REST 限额实测为每小时 60 次，任务书摘要里没有给后端配只读 Token、没有缓存与新鲜度设计，`POST /refresh` 一刷就可能把限额烧光。
2. **写接口没有鉴权（第 5 项，中）**：`notes` / `todos` 的 POST/PATCH/DELETE 与 `POST /refresh` 只靠 SSH 隧道挡人，摘要里没有任何应用层鉴权说明；隧道一旦多人共用，写操作即无门禁。
3. **冻结顺序反了（第 10 项，中）**：首批接口清单已列出，但 T-006 的数据调查尚未交付；`last_error` 残留语义、`NEEDS_ATTENTION` 非终态、48 小时/7 天升级机制未实现等口径若不先落进数据模型，OpenAPI 冻完就要返工。

其余中风险：第 2 项（GitHub 与本地状态分离的口径与单点故障）、第 6 项（本地文件白名单未精确化）、第 7 项（Worktree 隔离靠约定、无技术强制）。低风险：第 1 项（复杂度可控）、第 3 项（FastAPI 适配）、第 4 项（SQLite 够用）、第 9 项（当前设计无公开泄露路径）。

**与已验证事实的冲突核查：摘要本身没有与已验证事实直接矛盾的陈述**，但有 2 处“写得像已证实、实际未证实”和 2 处口径待澄清，见文末“与已验证事实对照”一节。全文无编造的数字、来源或风险；无密钥、无 Token。

## 1）当前架构是否存在不必要的复杂度

- **风险等级：低**
- **结论：无结构性过度设计。** 技术栈是常规组合，前后端分离、FastAPI + SQLite、不引入不必要的中间件，规模与“单人使用的内部总控台”匹配。唯一可简化的是前端动效与图表库，但不构成架构问题。
- **证据**：
- 任务书 v1.1 摘要：前端 React + TypeScript + Vite + Tailwind CSS + shadcn/ui + Framer Motion + TanStack Query + ECharts；后端 Python + FastAPI + Pydantic + SQLite + pytest；“不引入不必要的中间件”。
- 仓库现状佐证“没有过度建设”：muse-hub 内无任何 `.py` 文件、无 FastAPI/Flask/uvicorn 相关代码（`find` 与全文检索均为空），Control Tower 目前确实是从零起步，不存在已落地的冗余组件。
- **发生条件**：首版若为追求视觉效果在 Framer Motion 动效与 ECharts 复杂图表上投入过多工时，会拖慢 Stage 0 交付；但不影响正确性。
- **建议解决方案**：保持主干不变；首版动效与图表按“够用”取舍（例如先以基础折线/柱状图满足总览需求），把省下的工时留给第 8 项的数据源方案与第 10 项的数据模型冻结。不强制换栈。

## 2）GitHub 与本地状态数据分离是否合理

- **风险等级：中**
- **结论：分离本身合理，但存在两个未定的口径：同一任务出现两套“状态”时以谁为准，以及本地状态只有一份、没有备份。**
- **证据**：
- 分离合理：GitHub 侧是公开协作数据（任务、BOARD、Issue、结果文件），本地侧是运行态数据（health、scan、events、receipts、日志）；仓库实测证实后者确实不在 GitHub 上——`find` 在整个 muse-hub 仓库内找不到 `health.json`、`scan.json`、`events/`、`receipts/`。
- 口径冲突真实存在：`BOARD.md` 第 4 行自述“本表是总控手动维护的状态表，不是实时事实；任务状态以远端提交和收据为准，表的状态可能滞后数小时”；`tasks/T-006-control-tower-data-survey.md` 第 46 行把“BOARD 完成 vs Issue OPEN”列为必须覆盖的冲突案例；`RULES.md` R6b（第 49 行）又定义了 `NEEDS_ATTENTION` 这一 BOARD 之外的事件状态。同一任务至少有 BOARD 状态、Issue 状态、事件状态三套说法。
- 单点故障：任务书已验证事实（第 44 行）确认关键状态文件“只在总控 VM 本地”；摘要与任务书中均无备份、同步或异地副本方案。
- **发生条件**：后端按摘要“统一读取、归一化”时，若直接取 BOARD 状态展示，遇 BOARD 滞后（数小时）即向总控展示过期状态；若总控 VM 磁盘故障，`events/` 与 `receipts/` 的历史验收链路即丢失，且 Tower 无任何备用数据源。
- **建议解决方案**：
1. 在数据模型中写死优先级：验收类状态以收据（receipts）与提交为准，BOARD 仅作展示参考，Issue 状态不参与任务状态判定（见第 10 项）。
2. 每个聚合响应带 `last_updated` 与数据来源标注，让前端能标明“BOARD 数据可能滞后数小时”。
3. 给总控 VM 本地状态文件定备份方案（定时快照到 VM 外位置，频率与保留期由总控定），再冻结数据模型。

## 3）FastAPI 是否适合现有 VM 环境

- **风险等级：低**
- **结论：适合。** FastAPI + SQLite + systemd 的组合轻量、无需容器、与“部署在总控 VM、systemd 管理”一致；首版只读聚合场景下性能不是瓶颈。
- **证据**：
- 摘要明确“部署在总控 VM，Linux systemd + SSH 隧道”；`RULES.md` R6b（第 46 行）与 `README.md`（第 13、15 行）证实现有运行设施就是 Bash/Python 脚本 + systemd 式 Hook 巡逻，Python 运行环境在总控侧已有使用先例。
- 反向证据：仓库内无任何后端代码与部署文件（`infra/` 不存在），因此不存在“现有环境与 FastAPI 冲突”的实证。
- **发生条件**：若总控 VM 的 Python 版本、pip 可用性、依赖安装方式未事先确认，首次部署可能卡在环境准备上；无容器化则“在我 VM 上能跑”是唯一保障。
- **建议解决方案**：冻结前确认总控 VM 的 Python 版本并写入部署说明；`requirements.txt` 钉死版本号、用 venv 隔离；保留已规划的 `GET /healthz` 作为 systemd 存活探针。以上均属实施细节，不动架构。
- **未验证**：总控 VM 的 Python 版本、systemd 配置、SSH 隧道现状均不在本节点可读范围（见文末清单）。

## 4）SQLite 是否满足第一版要求

- **风险等级：低**
- **结论：满足。** 首版只存 Control Tower 自有数据（备注、待办），单人使用、读多写少、无多节点并发写入，SQLite 完全够用。
- **证据**：摘要明确“SQLite 只保存 Control Tower 自己产生的数据，不建立第二套 GitHub 任务数据库”；首批接口中只有 `notes` 与 `todos` 两组写接口，其余均为读接口，写负载极低。
- **发生条件**：两种情况会超出 SQLite 的舒适区——(a) 后台刷新任务与用户编辑同时写库且未开 WAL 模式，可能出现写锁等待；(b) 数据库文件损坏或误删且无备份，备注与待办即丢失。两种情况首版概率均低，但备份缺失与第 2 项的本地单点故障是同一根源。
- **建议解决方案**：开启 WAL 模式；数据库文件放仓库之外（摘要已有此要求）；纳入第 2 项建议的备份方案；暂不需要引入 PostgreSQL 或其他外部数据库，若日后多用户再评估。

## 5）私有访问方案是否安全

- **风险等级：中**
- **结论：网络层方案合格，应用层鉴权缺失。** “不公开监听公网端口 + 首版通过 SSH 隧道访问 + systemd 管理”挡住了公网扫描与未授权网络接入；但摘要里没有任何应用层鉴权设计，写接口的安全完全寄托在隧道这一道门上。
- **证据**：
- 摘要安全要求逐条列出“不公开监听公网端口；首版通过 SSH 隧道访问；使用 systemd 管理服务”，方向正确。
- 缺口在接口清单本身：`GET/POST/PATCH/DELETE /api/v1/notes`、`GET/POST/PATCH/DELETE /api/v1/todos`、`POST /api/v1/refresh` 均为写/触发操作，而摘要全文没有任何“登录、Token、鉴权、鉴权失败处理”的设计；“私有访问”的覆盖人群（仅 Chen？是否含各节点？）也未定义。
- 现状佐证：`infra/` 与任何部署配置均不存在，隧道与访问名单目前无落地的可查配置。
- **发生条件**：SSH 隧道接入方超过总控一人（例如为方便节点查看而共享隧道），或日后任一环节把服务端口暴露出来，任何能到达后端的人无需鉴权即可改备注、删待办、反复触发 `POST /refresh` 烧 GitHub 限额。
- **建议解决方案**：
1. 冻结前明确隧道接入白名单（建议首版仅总控一人），并写入部署说明。
2. 在写接口上线前补最低限度的应用层鉴权（例如后端校验的固定 Bearer Token，存于仓库之外，与 GitHub Token 分开管理）；或将首版写接口限制为“仅本机回环可写”。
3. SSH 密钥的保管与轮换规则由总控另行明确，不写入公开仓库（`RULES.md` R5 第 31 行红线）。

## 6）后端读取本地文件的权限设计是否合理

- **风险等级：中**
- **结论：方向正确（白名单 + 禁任意文件读取 + 禁远程 Shell），但白名单是空壳：具体路径、运行身份、遍历防护均未定义，无法据此评审实现。**
- **证据**：
- 摘要安全要求：“后端只能读取白名单路径；不提供任意文件读取接口；不提供远程 Shell 执行功能；SQLite 数据放在仓库之外。”
- 但摘要没有列出白名单包含哪些路径；`RULES.md`、`README.md`、`ONBOARDING.md` 中也没有任何白名单清单。唯一可查的本地路径清单来自 T-006 任务书提供的脱敏样本（`tasks/T-006-control-tower-data-survey.md` 第 54–60 行）：`health.json`、`scan.json`、`events/*.json`、`receipts/*.json`、`logs/health-exceptions.jsonl`，且这些样本文件本身只在总控 VM 上，本节点无法独立核对（见未验证清单）。
- 风险来源是实现方式而非意图：若白名单以“路径前缀匹配”实现且不做规范化与符号链接解析，`../` 或符号链接可绕过白名单读到白名单外的文件。
- **发生条件**：后端实现阶段，任一按用户输入拼接路径的接口（如按任务编号取事件文件）未做严格校验，即可能越界读到 VM 上其他文件；后端若以高权限用户运行，越界读取的影响随之放大。
- **建议解决方案**：
1. 在数据模型冻结时把白名单写成精确的绝对路径清单（只含上述五类状态文件），不接受目录级通配。
2. 实现要求：解析符号链接、规范化路径后再校验白名单；按 ID 取文件时先校验 ID 字符集，禁止 `/`、`.` 与 `..`。
3. 后端以专用低权限 OS 用户运行，对状态文件仅授读权限；日志中不得输出文件绝对路径之外的敏感内容。

## 7）前后端 Worktree 隔离方案是否可靠

- **风险等级：中**
- **结论：隔离意图合理，但 Worktree 本身不提供访问隔离；“不得擅自进入”是规则而非技术控制，责任映射也不完整。**
- **证据**：
- 摘要：“使用独立 Worktree：backend 由 Codex、frontend 由 Antigravity、integration 由总控；三个辅助节点以研究、测试和审查为主，不得擅自进入其他模型的工作目录修改代码。”
- 现状：仓库内存在共享技能 `skills/direct_codex_antigravity/`（`SKILL.md`、`skill.yaml`），说明 Codex/Antigravity 协作方式已有约定；但 `muse-control-tower` 仓库与任何 Worktree 均不存在（见第 8 项证据），隔离方案尚无落地物可查。
- 规则依据：`RULES.md` R1 只定义了四个账号（总控、1 号、2 号、3 号），Codex 与 Antigravity 是工具而非账号——“谁操作 Codex 写 backend、谁操作 Antigravity 写 frontend”在摘要中没有映射到 node-1/2/3，责任边界不完整。
- **发生条件**：同一 VM、同一 OS 用户下，任何参与者 `cd` 进另一 Worktree 即可修改代码；Worktree 只是不同的工作目录，不做权限隔离。若集成阶段出现跨 Worktree 的未评审修改，问题要到总控集成时才被发现。
- **建议解决方案**：
1. 明确映射：哪个节点操作哪个工具、产出归属哪个 Worktree，写入总体任务书或分工说明。
2. 二选一并写进方案：(a) 接受“约定 + 总控集成评审”的轻量模式，明确总控集成时逐提交核对作者与 Worktree；或 (b) 用独立 clone 或不同 OS 用户做硬隔离。首版建议选 (a)，但必须明文写下，而不是默认大家都会遵守。
3. 沿用现有规则：集成只合入经评审的提交；`RULES.md` R3 的目录隔离原则同样适用于 Tower 仓库。

## 8）是否存在数据源不可访问的风险

- **风险等级：中**
- **结论：存在，且是本次审查中最具体的可量化风险。GitHub 未认证限额与本地状态单点存放两条线都有实测或实证支撑。**
- **证据**：
- GitHub 限额实测（2026-11-12，未认证 `GET https://api.github.com/rate_limit`）：`X-RateLimit-Limit: 60`，`X-RateLimit-Remaining: 59`，`X-RateLimit-Used: 1`。任务书已验证事实（第 44 行）“GitHub 未认证 REST 限额每小时 60 次量级”属实。
- 摘要未给后端配任何 GitHub Token（全文无 Token 存储、轮换方案），而首批接口每次刷新至少涉及任务、BOARD、Issue、结果文件等多类读取；若 `POST /refresh` 被频繁触发或前端高频轮询，60 次/小时的限额很快耗尽，Tower 即无新数据。
- 本地状态不可访问的另一面：仓库实测无 `health.json`/`scan.json`/`events/`/`receipts/`；任务书确认其“只在总控 VM 本地”。后端若不在总控 VM 上运行，本地数据源整条不可用；总控 VM 宕机时 Tower 同样无数据，且摘要无缓存降级设计。
- 静态 Space 原型是第三个数据源风险点：任务书称其“数据写死快照”，若 Tower 首版回退到该快照，用户将看到过期数据而无从察觉（原型内容与可见性未验证，见文末清单）。
- **发生条件**：(a) 未认证调用超出 60 次/小时；(b) 总控 VM 宕机或磁盘故障；(c) 后端部署位置变更离开总控 VM；(d) 展示层把快照数据当实时数据。任一发生即导致总览缺数或错数。
- **建议解决方案**：
1. 为后端申请最小权限只读 GitHub Token（Contents: read 级别即可），存于仓库之外并定轮换周期；该 Token 是新增凭据，需按 `RULES.md` R5 与 R17 走 Chen 批准的授权路径，不得写入公开仓库。
2. 后端加缓存与新鲜度标注：GitHub 数据缓存、每次刷新记录 `fetched_at`，超限或失败时展示旧数据并明确标注“数据截至 X 时，可能过期”，不得静默展示过期数据当作实时数据。
3. 明确降级策略：GitHub 不可达与本地文件不可读时各端点返回什么、前端如何提示，写入 OpenAPI 说明。

## 9）是否存在公开仓库泄露内部运行信息的风险

- **风险等级：低**
- **结论：按当前设计无泄露路径。** Tower 只读公开库、SQLite 与运行数据均在仓库之外、首版不得自动修改 muse-hub，三条边界合起来堵住了已知的泄露口。剩余一项未验证点需总控确认。
- **证据**：
- 摘要：“SQLite 只保存 Control Tower 自己产生的数据”；“所有密钥、数据库和生产运行数据不得提交进仓库”；“第一版不得自动修改 muse-hub”；“前端只访问后端 API，不直接读取 GitHub Token 或总控 VM 文件”。
- 仓库现状：muse-hub 是公开库，但本次审查的交付物与既有结果文件均不含密钥（`RULES.md` R5 第 31 行为红线）；本地状态文件不在仓库内，无从通过公开库外泄。
- **发生条件**：(a) 日后某版本把 Tower 的备注、日志或运行数据写回 muse-hub，泄露口即打开；(b) 静态 Space 原型的快照若含有内部运行信息且该 Space 公开可见，则泄露已经存在——但原型内容与可见性本节点无法核实（见未验证清单），此处不下结论。
- **建议解决方案**：
1. 把“运行数据与备注不得写入 muse-hub”作为长期红线保留在 Tower 仓库说明中，而不仅是首版要求。
2. 总控核查静态 Space 原型的可见性与快照内容，确认不含内部运行信息后再决定其去留；核查结果建议由总控在 Stage 0 汇总中记录。
3. 后端错误响应不得回显本地绝对路径、Token 或异常堆栈。

## 10）是否有影响后续扩展的结构性问题

- **风险等级：中**
- **结论：有两处结构性隐患，都是现在不定、以后返工的类型：OpenAPI 冻结顺序与状态口径未对齐；单租户假设 baked in。**
- **证据**：
- 冻结顺序：摘要称“首批接口（以冻结的 OpenAPI 为准）”，但 T-006 的数据调查（`tasks/T-006-control-tower-data-survey.md`）与本审查并行、尚未交付；其样本揭示的状态口径——`health.json` 的 `last_error` 是“最后一次错误”而非“当前错误”（成功运行时仍残留旧值，T-006 第 54 行）、`NEEDS_ATTENTION` 不是终结状态且“48 小时归类与 7 天升级两级机制尚未在代码中实现”（`RULES.md` R6b 第 49 行）、`scan.json` 的 `s3_ledger` 字段、`events/*.json` 的 `retry`/`approval` 结构（T-006 第 56、58 行）——在现有 11 个端点中没有对应的表达位置。
- 口径陷阱实测：Issues #1～#5 全部为 OPEN（2026-11-12 未认证 API 实测，评论数分别为 2、2、0、0、0），而 BOARD 上 T-001～T-005 全部完成——Issue 状态不参与流程是现行规则（T-006 第 52 行亦有相同结论），但任何按“ Issue open = 任务未完成”直觉实现的 `/api/v1/tasks` 都会系统性错判。
- 单租户假设：摘要无用户、权限、审计概念；`notes`/`todos` 无归属字段；后续若要多用户或节点自助查看，鉴权与数据隔离需重做而非扩展。
- **发生条件**：OpenAPI 按现有 11 个端点冻结后，T-006 的字段映射才发现缺口（例如 `/api/v1/runtime` 无法表达 `last_error` 的残留语义、`/api/v1/events` 无法表达 `NEEDS_ATTENTION` 的人工待归类含义），即需破版修订；多用户需求出现时同理。
- **建议解决方案**：
1. 调整冻结顺序：先等 T-006 交付字段映射表，再冻结数据模型，最后冻结 OpenAPI；本审查报告与 T-006 报告由总控汇总后交 ChatGPT 定夺（按任务书目标）。
2. 所有聚合端点（尤其 `/api/v1/overview`、`/api/v1/tasks`、`/api/v1/runtime`）统一带 `last_updated`、`source` 与 `stale` 标记；`last_error` 字段在 API 中改名或加注，禁止前端将其渲染为“当前故障”。
3. `/api/v1/tasks` 的状态机以“收据/提交 > BOARD > Issue 状态（不用）”为准绳写入数据模型说明；事件状态枚举须包含 `NEEDS_ATTENTION` 的“待人工归类”含义。
4. 接受首版单租户定位并明文写下；若未来要多用户，届时以 v2 评估，不为此提前过度设计。
